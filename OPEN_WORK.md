## Backlog

- [ ] **[toolkit] The `series` contract still materialises every station before the build starts — make it an iterator** (the second half of the chunked-write fix; the first half is DONE, see below). `build_local(..., series: dict)` and `fetch_all(...) -> {ref: (times, values, extras)}` mean the caller holds every station's arrays at once: ~24 B per stored observation, measured **784 MB for ECan groundwater**. That is now the *entire* remaining floor of the build — the planes are gone. Fixing it needs both halves: `build_local` accepting an iterable of `(ref, times, values, extras)`, and the source adapters *yielding* per station (`envlib-ingest-ecan-env/qa/source.py`, `raw/source.py`).
  **The real design work is the two-pass problem:** the time-axis extent must be known before any row can be written (`build_local` currently reduces `min`/`max` over the whole dict), so either the caller declares the span, or the source must be re-iterable rather than a one-shot generator, or a cheap metadata pre-pass collects per-station min/max. Decide explicitly.
  Breaking change ⇒ **0.2.x → 0.3.0**. Blast radius is small: `envlib-ingest-ecan-env` is the only consumer (`envlib-ingest-esa-sst` has its own grid publish path). Per-station validation (`_check_aligned`, `_check_extras`, `_qc_filter`, `_non_empty`) is already single-pass with no cross-station state, so it folds into the streaming loop; `_check_refs` needs only the key set.

- [ ] **[tethys] BLOCKER for every tethys migration: `tethysts` and this toolkit cannot share an environment** (found 2026-08-03, building the ECan QC migration). `tethysts` → `pandas<2` → the numpy 1.x C ABI; `envlib-ingest-base>=0.2.0` → `cfdb>=0.9.4` → `numpy>2`, and that cfdb floor is asserted at RUNTIME (older cfdb fabricates values through packed dtypes, so it cannot be relaxed). `uv` reports the pair as flatly unsatisfiable — there is no pinning that reconciles them, and splitting locks does not help because neither side is individually satisfiable *together with* the other in one process. It surfaces in stages, so expect confusion: pandas 1.5.3 has no cp312 wheel; capping Python at 3.11 gets it installed; it then dies at import with `numpy.dtype size changed ... Expected 96 from C header, got 88`; only pinning `numpy<2` makes uv state the real conflict. **Resolution adopted: a standalone tethys→netCDF4 archiver** (own repo, own venv, quarantined legacy pins, retired when the migration completes) that faithfully exports each tethys dataset with ALL its metadata; the `envlib-ingest-*` repos then read that export with xarray in the modern environment and never see tethysts. This also backs up single-copy archives and covers datasets envlib cannot represent (e.g. 30 of ECan's 36 QC'd datasets are irregular). Getting its own plan. **Verified escape hatch if a direct reader is ever wanted instead:** a tethys result chunk decodes completely with `zstandard` + `xarray(engine='scipy')` on numpy 2.3.2 — note the chunks are netCDF-3 classic, so `h5netcdf` fails and the scipy engine is required.
- [ ] **[toolkit] No deletion path — the merge cannot express a retraction** (found during the 2026-08-03 ancillary-variable round; Gemini flagged it, diagnosis corrected on inspection): `merge_dataset` writes "incoming non-NaN wins", so an all-NaN incoming slot leaves the stored value untouched. That is **deliberate and load-bearing** — it is exactly what stops a briefly-offline station from erasing good history (`tsortho.py` module docstring) — but it means a source that legitimately revises a reading *to* missing has no way to say so, and the toolkit has zero delete/retract functions.
